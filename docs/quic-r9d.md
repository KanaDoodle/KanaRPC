# QUIC 小请求吞吐稳定性与优化评估（R9D）

以 R9C `c02d770` 和 R9B `0b33dad` 为内部基线，通过串行配对负载与 profile 判断小请求差异是否稳定，并评估收尾同步的优化候选。

## 复验与候选评估

1. **复现稳定性**：冻结两版代码和公共实验 driver。先重复原 128B / managed 两连接 / 8 协程 / 1000 次短跑，再将每组延长到 20000 次、增加到 15 个种子，交替版本先后。记录完整 offered、p95/p99、三进程 CPU、每对变化、范围与 bootstrap 描述区间。以配对分布判断原 −6.1% / −3.4% 差异的稳定性；对照串行执行，与测试和 profile 分开。
2. **定位开销**：审查 R9C 新增的回执结算与收尾锁/Context 观察，以微基准和 CPU/mutex/alloc profile 验证。profile 与吞吐验收分开，公共 profile driver 注入全部版本；保留没有定位到目标开销的负结果，不通过删指标改语义换速度。
3. **最小优化**：仅优化已经确认的重复同步/分配；保留 BudgetError、池级预算、退休计费、首次 CANCEL 观察、ACK 结算截止点与幂等、迟到 ACK 不翻转故障、请求 deadline 与通道 cause 区分、累计交付故障以及带期限 drain。不改 QUIC reset 安全写法，不做无关重构。
4. **回归与内部基线**：每个候选先通过针对性/race 和三传输故障测试，再用固定代码串行比较 R9B/R9C/最终版本，包含小请求普通/流式以及 TCP、大包对照；保留无收益、失败与退化，最终补完整 Go 普通/race、最低 Go 版本、SDK、有限资源与饱和 drain 验证。

## 验证范围与结论

验证包含针对性 race、资源检查与最终内部对照。最终主对照为 5 对、每组 10000 次；此前完成的 15 对稳定性复验及全部负结果一并保留。

- ACK 是协议回执，不证明用户消费或业务提交。回执结算前观察到 ACK 优先，结算后迟到 ACK 不抹去累计故障。
- 首次 CANCEL 与最终结算分别统计；Context 取消原因和自身 deadline 使用独立判定。
- 最终基线使用冻结源码后的串行运行；报告分别列出短跑、延长负载与局部微基准，区间用于描述本轮样本。

完成情况与实际证据见 [验证报告](verification/quic-r9d/report.md)。

实际结论：原降幅没有稳定复现；三个提前返回候选均未证明整体吞吐收益，且出现局部负变化，最终全部撤回。库代码保持 R9C，本轮保留可重放的诊断、配对分析工具、必要边界用例与负结果。报告末尾提供可重放的诊断命令。
