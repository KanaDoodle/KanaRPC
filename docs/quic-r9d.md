# R9D：验证并处理 R9C 小请求吞吐退化

起点 R9C `c02d770`，内部参考 R9B `0b33dad`。仅修改 KanaRPC；不做 gRPC 对照，不触及 CampusTrace。
真实双机、物理 WAN/NIC、GPU/vLLM 未验证；所有负载是本机 JSON fixture。

## 实现前步骤

1. **复现稳定性**：冻结两版代码和公共实验 driver。先重复原 128B / managed 两连接 / 8 协程 / 1000 次短跑，再将每组延长到 20000 次、增加到 15 个种子，交替版本先后。记录完整 offered、p95/p99、三进程 CPU、每对变化、范围与 bootstrap 描述区间。不得先假定原 −6.1% / −3.4% 是稳定的代码回归；串行执行，期间不并跑本轮测试或 profile。
2. **定位开销**：审查 R9C 新增的回执结算与收尾锁/Context 观察，以微基准和 CPU/mutex/alloc profile 验证。profile 与吞吐验收分开，公共 profile driver 注入全部版本；保留没有定位到目标开销的负结果，不通过删指标改语义换速度。
3. **最小优化**：仅优化已经确认的重复同步/分配；保留 BudgetError、池级预算、退休计费、首次 CANCEL 观察、ACK 结算截止点与幂等、迟到 ACK 不翻转故障、请求 deadline 与通道 cause 区分、累计交付故障以及带期限 drain。不改 QUIC reset 安全写法，不做无关重构。
4. **回归与内部基线**：每个候选先通过针对性/race 和三传输故障测试，再用固定代码串行比较 R9B/R9C/最终版本，包含小请求普通/流式以及 TCP、大包对照；保留无收益、失败与退化，最终补完整 Go 普通/race、最低 Go 版本、SDK、有限资源与饱和 drain 验证。

## 验收约束

用户在执行过程中要求收缩对面试展示无帮助的测试。因此后续只完成保护本次改动的必要 race、已启动的资源检查及一组简化的最终内部对照，不再追加 fuzz、长测或边缘场景矩阵。最终主对照缩为 5 对、每组 10000 次；前面已完成的 15 对稳定性复验和所有负结果继续保留。

- ACK 是协议回执，不证明用户消费或业务提交。回执结算前观察到 ACK 优先，结算后迟到 ACK 不抹去累计故障。
- 首次 CANCEL 观察不等于它赢得结算；context 的取消原因和 deadline 判断不能合并为“全部主动取消”。
- 最终基线只能使用冻结源码后的串行运行。短跑中位数变化与局部微基准不能冒充整体稳定收益；置信区间是本轮样本描述，不是生产保证。

完成情况与实际证据见 [验证报告](verification/quic-r9d/report.md)。

实际结论：原降幅没有稳定复现；三个提前返回候选均未证明整体吞吐收益，且出现局部负变化，最终全部撤回。库代码保持 R9C，本轮保留可重放的诊断、配对分析工具、必要边界用例与负结果。面试可直接使用报告末尾的短命令重放，无需展示无关测试数量。
