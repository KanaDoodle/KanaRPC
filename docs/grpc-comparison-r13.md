# grpc-go 同条件对照 · R13

## 目标与复现

比较相同业务负载下的普通和服务端流式调用，量化当前传输快路径的吞吐、延迟和进程开销。框架实现保持不变，新增代码位于独立的 [tools/grpc-compare](../tools/grpc-compare) 模块。

```sh
python3 scripts/compare-grpc.py --smoke --race --duration 0.2 --repeats 1 --output /tmp/grpc-race-new
python3 scripts/compare-grpc.py --duration 2 --repeats 4 --output /tmp/grpc-paired-new
python3 scripts/summarize-grpc.py /tmp/grpc-paired-new
```

## 统一条件

| 项目 | 设置 |
| --- | --- |
| 源码与工具链 | KanaRPC 基线 7b63b80；grpc-go v1.85.0；Protobuf v1.36.12；Go 1.27.3 |
| 运行方式 | 本机 loopback，独立客户端/服务端进程，每进程 GOMAXPROCS=4 |
| 传输 | 明文 TCP、TLS 1.3；相同证书算法与信任校验方式 |
| 连接 | 一个复用的物理连接；每次运行检查接受连接数恰好为 1 |
| 数据与业务 | 同一 `.proto`、相同处理函数；逐片验证 payload、顺序和结束 |
| 负载 | 普通调用 64 B/4096 B 字符串；流式 8×1024 B；并发 1/16 |
| 测量 | 每组 64 次顺序预热后运行 2 秒，四轮；客户端停止发新请求后等待已有请求完成 |
| 限额 | 客户端每次调用 2 秒；服务端请求/HTTP2 流限额 128，帧/消息上限 1 MiB |
| 重试与功能 | 关闭配置重试；grpc-go 库自带透明传输重试行为保留；不启用压缩、发现或治理控制器 |
| 顺序 | 场景固定种子打乱；四轮中每组各两次 Kana→gRPC、两次 gRPC→Kana |

grpc-go 按[官方建议](https://grpc.io/docs/guides/performance/)复用 channel/stub；没有为请求单独建连。版本固定为核查时的[稳定版 v1.85.0](https://github.com/grpc/grpc-go/releases/tag/v1.85.0)。生成器版本独立固定为 v1.6.2。

测试按成功调用数/实际测量时长统计吞吐，流式单位是完整 RPC，每个包含 8 个片段；不把片段数当请求数。延迟从调用发起到完整结果/终态结束，覆盖全部尝试；失败单独保留，不剔除。客户端与服务端 CPU、分配量均为各自进程在测量前后的差量，包括框架及少量采样开销，不是纯业务函数成本。

这是封闭并发负载：每个 worker 等待整次调用完成后再发下一次。因此两端固定的是并发和时长，总调用数不同；它不是固定到达率下的过载实验。

## 结果

2026-11-01，macOS / Apple M5，非独占桌面环境。96 次正式运行、7,407,043 次调用，失败为零；各运行均满足连接数、业务接纳数和服务退出检查。以下是四轮中位数，吞吐列为完整 RPC/s，p95 列为微秒。

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| TCP | 普通 64 B | 1 | 24,904 | 24,030 | 51 | 53 |
| TCP | 普通 64 B | 16 | 49,719 | 119,480 | 460 | 220 |
| TCP | 普通 4096 B | 1 | 21,347 | 22,910 | 77 | 54 |
| TCP | 普通 4096 B | 16 | 38,746 | 89,555 | 633 | 322 |
| TCP | 流式 8×1024 B | 1 | 9,188 | 19,426 | 196 | 68 |
| TCP | 流式 8×1024 B | 16 | 17,941 | 72,960 | 1,233 | 383 |
| TLS | 普通 64 B | 1 | 22,320 | 22,474 | 61 | 66 |
| TLS | 普通 64 B | 16 | 51,395 | 116,392 | 446 | 226 |
| TLS | 普通 4096 B | 1 | 19,871 | 21,564 | 80 | 57 |
| TLS | 普通 4096 B | 16 | 35,190 | 84,156 | 729 | 331 |

64 B 单并发接近，但并不形成稳定领先：四轮配对吞吐比 Kana/gRPC 在 TCP 为 0.858..1.046，TLS 为 0.885..1.111。并发 16 的普通调用中位数约为 grpc-go 的 42%..44%，流式为 25%..29%。存在轮次波动，例如 TCP 4096 B/并发 16 的配对比为 0.184..0.455；所有样本均保留，没有挑选有利轮次。

## 协议差异与解释

统一的是业务数据、客户端并发、运行环境和可对应的配置。KanaRPC 使用 KNR2 的 DATA/END/ACK 和信用消息、连接/字节租约；grpc-go 使用 HTTP/2/gRPC 的数据、trailers 和字节流控。双方均保留各自缓冲与流控实现，KanaRPC 信用窗口为 32、默认字节预算保留；grpc-go 使用默认自适应 HTTP/2 窗口。框架级完成和资源结算语义并非相同协议。

这份结果表明，当前版本在高并发和多片流式传输上存在明确的吞吐、CPU 与分配差距。本轮没有修改框架去配平，也没有把差额直接归因于 ACK、锁或缓冲某一项；具体优化需要另做 profile 和针对性对照。

本轮只比较 TCP/TLS。原生 QUIC 使用独立请求流，与这里的 HTTP/2/TCP 不属于同传输条件，未并入排名。没有测量过载公平性、取消尾部、故障交付、发现一致性或长时资源表现，不以本表推断这些维度。

## 验证与证据

race 冒烟覆盖两个框架、两种传输和三种负载，共 12 次独立进程运行，调用结果和服务退出通过；这些速度数据不进入正式表。根模块只读构建通过。首次编写工具时有一处括号缺失，编译器拒绝，修正后完成正常/race 构建；不涉及 RPC 内核修复。

源码在正式测量期间保持冻结，串行执行且没有性能采样器。主机未做 CPU 绑核或独占隔离，结果是有限时长本机比较，不是物理双机、WAN、生产容量或模型推理收益。

[验证目录](verification/grpc-r13/manifest.json)保存工具链、依赖、源码 SHA-256、完整结果、race 与正常运行原始数据，以及自有进程回收状态。后续优化应保留本轮基线，在相同环境和同一测试工具下重新对照。
