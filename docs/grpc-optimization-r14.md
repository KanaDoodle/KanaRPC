# R14：并发与流式调用的 profile 定位和优化

## 目标与实施顺序

R13 的同机双进程对照暴露了两个问题：并发 16 时普通调用吞吐明显落后于 grpc-go，流式调用的 CPU 与分配成本更高。本轮以 R13 内核为冻结基线，先采集客户端和服务端 CPU、allocs、mutex、block profile，再逐项验证候选，最终重新运行三方交替对照。CampusTrace 未修改。

| 阶段 | 操作 | 证据 |
| --- | --- | --- |
| 定位 | TCP/TLS、并发 16、64 B/4096 B 普通调用及 8×1024 B 流式调用，两端分别采样 | `profile-before`，12 组，3 秒/组 |
| 候选 A | 状态通知通道按等待需要创建 | `lazy`，原内核/候选/grpc 三方，36 组 |
| 候选 B | 在 A 上合并已消费块的 CREDIT 返还 | `credit`，原内核/候选/grpc 三方，36 组 |
| 候选 C | 在 B 上对大 TCP 帧使用 writev | `writev`，B/候选/grpc 三方，36 组 |
| 正确性 | 全量普通/race、跨窗口、取消、预算、回执与 drain | 独立真实单成员 etcd；另有双进程 race 验证 |
| 最终对照 | 原内核/最终内核/grpc，短流与跨窗口长流 | `final`，完整矩阵、每组 4 次，每次 2 秒 |

证据目录：[verification/grpc-r14](verification/grpc-r14/)。历史 R13 原始记录保持原样。

## pprof 发现与代码对应

采样期间开启了 CPU、mutex（fraction=1）与 block（rate=10000）profile。采样结果用于定位；所有性能表使用关闭 profiling 的独立运行。

1. **逐帧系统调用和唤醒是主要热点。** 原版本 TCP 8×1024 B、并发 16 的服务端，CPU profile 中 `wire.Write → net.Conn.Write → syscall.write` 累计约 37%，`wire.ReadReserved → net.Conn.Read` 约 21%。客户端每消费一个 DATA 都同步发送一个 CREDIT，信用尚未耗尽也会执行 writer 获取、写 deadline、取消回调和 socket 写入。grpc 的 profile 则能观察到 `loopyWriter` / `bufWriter.flushKeepBuffer` 路径。两种传输实现的发送组织方式存在直接差异。
2. **通知通道存在无等待者分配。** 64 B 并发 16 的客户端，`clientAdmission.notify` 占采样分配字节约 15%；服务端 `Server.notifyLocked` 约 8%。准备、编码和状态更新持续关闭并新建通道，即使没有调用正在等待这些通知。
3. **流式发送发生正文二次拷贝。** 原版本 TCP 流式服务端，`wire.Write` 占采样分配约 35%，Protobuf marshal 约 33%。已经编码的正文又被复制进 `header+payload` 连续帧。该拷贝用于保持单次写入，TLS 与 QUIC 的现有发送路径仍需要保留。

mutex/block profile 也观察到 writer、请求状态锁和等待者开销，但正常网络等待与服务端执行等待本就会进入这些样本，不能将全部等待时间解释成锁竞争。未据此放宽资源边界或替换请求状态机。

## 修改及行为契约

**按需通知。** admission、pending、server 和 execution 只在持有原有互斥锁且确有等待需要时创建当前通知通道。状态变更关闭已有通道并清空指针；下一次等待再订阅新一代通知。覆盖 `WaitIdle`、`Recv`、`Close`、`Server.Wait`、drain 和 QUIC session barrier 的等待路径，避免遗漏唤醒。

**合并信用返还。** 每消费一个块增加一个计数，到 `max(1, window/2)` 时一次写入多条普通 `CREDIT=1`，最多 16 条。窗口 1 仍立即返还；未消费的数据不获得信用。短流可在初始窗口内完成，END 后剩余计数随调用退休。线上格式不变，旧接收端逐条解析即可；没有新增后台 goroutine、定时刷新或持久队列。

整批 CREDIT 在分配 packet 前，按 `count×24` 字节预留 control-send 预算，直到成功、超时或取消后释放。批量写复用原 writer、deadline 与取消回调的停止/会合逻辑；发生可能的部分写入后，调用方按原规则关闭有序连接。credit 与 END/ACK 仍由 `creditMu` 协调。

**TCP writev。** 具体类型为 `*net.TCPConn`、正文至少 1024 B 的帧，使用 `net.Buffers.WriteTo` 把 24 B header 与已有正文交给 socket 的 writev 路径，省去正文大小的拼帧分配与拷贝。小帧、TLS、QUIC 和自定义连接包装器保持原连续帧写入。仍按原完整帧大小保守预留发送预算，未新增未记账的空闲缓存。

取消、END 回执、QUIC FIN、累计交付故障和 drain 的状态结算规则保持不变。没有通过关闭预算、跳过 ACK、提前宣称 drain 成功或自动清零故障来换取吞吐。

## 阶段候选与负结果

候选阶段均为并发 16、每条件两轮、每轮一秒的短对照，用于筛选；正式结论见最终四轮对照。

- **A 降低分配，不构成稳定的流式吞吐优化。** 客户端每 RPC 分配下降约 1–1.7 kB；TCP/TLS 流式吞吐相对原内核分别下降约 2.8% / 1.8%。保留该结果，采用理由是消除无等待者通道分配。
- **B 的直接收益出现在流式控制路径。** 相对原内核，TCP/TLS 短流吞吐中位数分别提高约 35% / 23%，仍明显低于 grpc。该结果需由完整复测确认。
- **C 主要减少分配。** 相对 B，TCP 流式服务端约从 27.1 kB/RPC 降至 18.7 kB/RPC，吞吐配对变化约 +0.1%；TCP 4096 B 普通调用约 +2.8%。TLS 4096 B 同期出现约 −1.8%，该路径未启用 writev，不能归因为 TLS 实现优化或退化。保留全部样本，不将内存收益写成稳定的流式吞吐收益。
- **开发过程失败记录。** A 初次修改遗漏 drain / QUIC barrier 的通知订阅，普通测试出现 QUIC 关闭和 drain 超时，并在并发 drain 用例中挂起，已停止并保留失败输出与 SIGQUIT 栈；补齐全部等待点后重新运行全量测试。新增测试也保留了初次窗口类型转换的编译失败日志。两者均发生在正式最终测量之前，修正后才进入验证。

## 最终同条件对照

Go 1.27.3、grpc-go 1.85.0、Protobuf 1.36.12；本机 Darwin/arm64、每进程 GOMAXPROCS=4。每组使用独立客户端/服务端进程、一条持久业务连接、同一 Protobuf 消息和 handler；TLS 为 TLS 1.3。64 次预热后闭环发起调用，每次请求 deadline 为 2 秒。普通调用与流式调用完成时验证完整响应、序号和 EOF；停止发压后计入尾部完成时间，保留所有 offered 请求。具体公共条件与协议差异沿用 [R13 方法说明](grpc-comparison-r13.md)。

三个版本串行运行，按条件/轮次轮换并反转顺序。冻结原内核与候选使用完全相同的 Go benchmark 程序、生成代码和依赖；runner 在构建前逐文件校验工具源码。完整矩阵为 TCP/TLS × 并发 1/16 × 普通 64 B、普通 4096 B、流式 8×1024 B、流式 64×1024 B，共 192 组。64 块长流超过初始信用窗口 32，实际覆盖多轮信用返还。

## 正确性与故障验证

- `go test`：独立真实单成员 etcd 3.7.3，**394 项通过（含子测试）、0 失败、0 跳过**。
- `go test -race`：同样的隔离 etcd runner，**394 项通过、0 失败、0 跳过**。
- 新增定向 race 回归重复 3 次：窗口 1/2/3/4/7/31/32 的多窗口完整传输与 drain、保留半窗信用后的取消、整批控制预算预留及拒绝、阻塞 CREDIT 写取消、真实 TCP 大帧 writev 阻塞写取消、碎片写下的普通 CREDIT 记录解析。
- 双进程对照程序 `--smoke --long-stream --race`：16 组，11,019 次请求，失败 0，全部完成 drain 校验。Race 下的吞吐不进入性能表。
- 根模块及独立 grpc 对照模块 `go vet ./...` 通过；对照输出的源码哈希在测量前后相等。
- 原 QUIC 微基准另做两轮 AB/BA：窗口 8、每 RPC 16 块、并行度 16、`Recv(nil)` 跳过业务解码。1024 B 样本 ns/op 从 131,195 / 121,358 到 110,244 / 109,842；16384 B 从 1,076,230 / 1,081,193 到 1,076,486 / 1,066,952，大块基本持平。原输出包含 B/op、allocs/op、包数与字节数。这是同进程局部微基准，不计入上面的双进程 grpc 表。

## 工程取舍与后续热点

剩余主要热点是每帧同步写入、逐帧读取、writer 等待和 Context/取消对象开销。普通调用还包含 OPEN 元数据、DATA、END 和终态 ACK 的完整生命周期；grpc 的 HTTP/2 写缓冲、流控与终态方式不同。后续更大幅度优化需要设计有界的连接级发送组织，并重新证明排队取消、部分写失败、字节记账和 drain 的行为；本轮保留现有状态机。

信用批量包最多预留 384 B 的 control-send 空间，窗口 1 仍为 24 B。大量 QUIC 流同时阻塞写且控制预算紧张时，批量包会提高瞬时控制占用；预算不足明确返回原有 BudgetError，未绕过限额或隐藏拒绝。TLS 仍有正文拼帧拷贝；本轮数据不足以证明普通调用全面提速。

测量范围为本机 loopback、非独占操作系统调度与有限时长运行。真实双机、WAN、小时/天级负载尚未验证；没有 vLLM 或推理性能结论。

```sh
# 解压冻结的原内核；新输出目录必须不存在。
mkdir -p /tmp/kanarpc-r14-frozen
tar -xzf docs/verification/grpc-r14/baseline-source.tar.gz -C /tmp/kanarpc-r14-frozen
python3 scripts/compare-grpc.py --focus --profile --duration 3 --repeats 1 --output /tmp/r14-profile-new

```

Profile 与性能运行串行执行；测量期间保持两个源码树不变并停止其他测试/压测。归档包含冻结源码、各候选源码、完整请求明细、两端 profile、测试日志、失败记录与校验值，目录结构见证据 README。
